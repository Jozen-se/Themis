# Test seams

The register the Build Brief's Test seams convention asks for (owner, 2026-10-18; D-26): every part of the
repository that exists only for development and tests, with its purpose, where it lives and how it is kept out of a
production build. Code that exists only for tests stays out of `Themis.Kernel.Contracts` and every other production
contract and has no effect on a production build. Every pull request that adds, moves or removes such a part updates
this table.

| Part | Purpose | Where it lives | How it stays out of production |
|---|---|---|---|
| Fixture module (`Themis.FixtureModule`) | A module shaped like a real one (five layers, own schema `fixture`, own role `themis_fixture`, two commands on `/v1/fixture/counters`) that the architecture, pipeline and role-model tests exercise without a real process module; its `failure` member injects a rejection, an exception, a serialization failure on the first attempt, a write to a kernel table or, since milestone 2 step 2b, a numeric overflow of its own column (RR-83: a 500, never a rule rejection) after the business write. | `tests/Fixtures/Themis.FixtureModule`; its schema, role and grants in `tests/Fixtures/Themis.FixtureModule/fixture-bootstrap.sql`, applied by the integration tests' `PostgresFixture` | Lives under `tests/`; referenced by the test projects only. `Themis.Host` never references it and never maps its routes; the architecture tests (ARCH-02, ARCH-03) fail on any reference from a kernel project. The compose and migrator bootstrap never create the `fixture` schema or role. |
| Fixture barrier and touch pair (`FixtureBarrier`, `TouchPair`, `ITrackedCounterStore`, `FixtureDbContext`) | The RR-40 test: a fixture command that adds to two counters in the given order through Entity Framework's SaveChanges and waits at a barrier between the two writes on the first attempt only, so two such commands in opposite order deadlock, PostgreSQL raises a real 40P01 wrapped in a DbUpdateException, and the pipeline's retry (D-41) lets both succeed. | `tests/Fixtures/Themis.FixtureModule/Application/FixtureBarrier.cs`, `TouchPairHandler.cs`, `tests/Fixtures/Themis.FixtureModule/Infrastructure/FixtureDbContext.cs`; route `/v1/fixture/counters/touch-pair` under `FIXTURE.TOUCH` | Part of the fixture module, which lives under `tests/` and is never referenced by the host; the barrier does nothing unless a test arms it. |
| Item create seam (`IItemCreateSeam`, `NoItemCreateSeam`) | A seam ITEM.CREATE calls after its duplicate pre-check and before it writes, so the RR-45 test can hold the first of two creates with the same item number while the second commits and prove that the unique index's violation is mapped to the R-MD-05 rejection. | `src/Kernel/Themis.Kernel.MasterData/ItemCreateSeam.cs` | Internal to the master data capability. `AddKernelMasterData` registers `NoItemCreateSeam`, which does nothing, with `TryAdd`; the production host has no other registration. |
| Item create test seam (`TestItemCreateSeam`) | The test implementation of the item create seam: runs whatever a test set after the pre-check. | `tests/Themis.Integration.Tests/Pipeline/TestSeams.cs`, registered by `PipelineTestHost` before `AddKernelMasterData` | Lives in the integration test project. |
| Test-only permissions `FIXTURE.TOUCH` and `FIXTURE.READ`, role `FIXTURE_TESTER` and the clerk's assignment | Lets the fixture module's touch command, and since milestone 2 step 2b the write-attempting query (RR-81), run under the real authorisation without borrowing a production permission (owner's decision on step 7, point 3). The other-site user of the identity test data holds the role at its site. | `tests/Themis.Integration.Tests/FixtureSchema.cs` (seeded as `themis_migrator` after the migrator ran); the test data in `tests/Themis.Integration.Tests/Identity/IdentityTestData.cs` | Not in `PermissionCatalog`, not in any seeder; the integration tests seed it into their own database. `Themis.Migrator` never writes it. |
| Posting hook (`IPostingHook`, `NoPostingHook`) | A seam the posting service calls after the ledger rows and cache updates are written and before it returns, so the acceptance tests can inject a failure after the inventory entries (R-LED-05, I-09) and a serialization failure on the first attempt (D-41). | `src/Kernel/Themis.Kernel.Posting/PostingHook.cs` | Internal to the posting capability since step 9 (it left `Themis.Kernel.Contracts`, owner's decision on step 8, point 1). `AddKernelPosting` registers `NoPostingHook`, which does nothing, with `TryAdd`; the production host has no other registration. |
| Posting failure switch and test hook (`PostingFailureSwitch`, `TestPostingHook`) | The test implementation of the posting hook: raises the failure the switch names, through the fixture module's injector, and since milestone 2 step 1 runs a delegate on the command's unit of work after the ledger writes, with which the RR-47 test plants an unbalanced journal line and lets the deferred trigger fail the commit. | `tests/Themis.Integration.Tests/Pipeline/TestSeams.cs`, registered by `PipelineTestHost` before `AddKernelPosting` | Lives in the integration test project, which sees the kernel's internals (`InternalsVisibleTo`). |
| Outbox relay seam (`IOutboxRelaySeam`, `NoOutboxRelaySeam`) | A seam the relay's pass calls after it has claimed its events and before it logs, updates and commits them, so a test can hold a pass while another runs or make it fail after the claim (D-53). | `src/Kernel/Themis.Kernel.Messaging/OutboxRelaySeam.cs` | Internal to the messaging capability. `AddKernelMessaging` registers `NoOutboxRelaySeam`, which does nothing, with `TryAdd`; the production host has no other registration. |
| Relay test seam (`TestOutboxRelaySeam`) | The test implementation of the relay seam: runs whatever a test set between the claim and the commit. | `tests/Themis.Integration.Tests/Pipeline/TestSeams.cs`, registered by `PipelineTestHost` before `AddKernelMessaging` | Lives in the integration test project. |
| Test token issuer (`Identity:TestIssuer`) | Lets the tests and local development mint HMAC-signed bearer tokens for any subject, so the real JWT bearer handler validates issuer, audience, signature and lifetime without an OpenID Connect provider (step 4 brief). | Configuration keys bound in `src/Kernel/Themis.Kernel.Identity/KernelIdentityServices.cs`; the tests' key and minting in `tests/Themis.Integration.Tests/Pipeline/TestTokens.cs` | The host refuses to start with the test issuer configured outside the Development, Test and Testing environments (`KernelIdentityServices.TestIssuerEnvironments`); production configures an authority instead. |
| Milestone 1 fixtures (`--fixture milestone-1`) | Test and development data: the organisation (installation, company SE01, site, warehouse, fiscal year 2026), the identity fixture (clerk, preparer, and since milestone 2 step 2a the settings administrator `33333333-3333-4333-8333-333333333333` with its assignment `00000000-0000-7000-8000-000000000406`, the only holder of SETTINGS_ADMINISTRATOR, RR-101; roles, assignments), the item posting group `TRADE_GOODS`, two accounts and two posting profile rules, two number series. | Definitions in `Themis.Kernel.Organisation`, `Themis.Kernel.Identity`, `Themis.Kernel.MasterData`, `Themis.Kernel.Posting` and `Themis.Kernel.Documents` (`Milestone1*Fixture`); the writers in `src/Kernel/Themis.Kernel.Persistence/Seeding` | Written only when `Themis.Migrator` runs with `--fixture milestone-1` (or `THEMIS_MIGRATOR_FIXTURE`); a production migration never passes it. The permission catalogue and the document type registry are system data, not fixtures, and are seeded on every run. |
| Integration test data (`IdentityTestData`, `MasterDataTestData`, the fiscal year 2027 of the posting tests, the three extra warehouses of the reporting view tests, the second site and the two site-limited settings administrators of `SettingScopeTests`) | Rows a test class needs beyond the fixtures (another site and warehouse, users with limited or expired assignments, a company without series, more warehouses for the D-54 allocation), written and removed by the test class. | `tests/Themis.Integration.Tests/Identity/IdentityTestData.cs`, `tests/Themis.Integration.Tests/MasterData/MasterDataTestData.cs`, `tests/Themis.Integration.Tests/Posting/InventoryAdjustmentPostingTests.cs`, `tests/Themis.Integration.Tests/Reporting/StockByWarehouseViewTests.cs` | Written as `themis_migrator` into the tests' own database (`SettingScopeTests` as the superuser into a seeded database of its own, dropped afterwards); no seeder or migration knows them. |
| Pipeline test host (`PipelineTestHost`) | An in-memory host wired like `Themis.Host` with the fixture module, the test seams, a capturing logger and a meter listener (the D-41 retries also per SQLSTATE, for R-LED-08); the relay's loop is off (`Outbox:Relay:Enabled` false) and the tests call the pass directly. Since step 11 it can run against another database on the fixture's server, the clone of a property run. Since milestone 2 step 2a a request to a settings route without a named subject runs as the settings administrator, every other one as the clerk (RR-101). | `tests/Themis.Integration.Tests/Pipeline/PipelineTestHost.cs` | Test project only; `Themis.Host` is the production composition root and registers none of the test seams. |
| Property-based test library (CsCheck) | The one property-based library of the repository (Build Brief, step 11): generators, shrinking and seeds for the invariant properties over the primitives, the fiscal calendar and, since step 11, the random command sequences through the pipeline. Apache-2.0, passes the licence scan. | `tests/Themis.Invariants.Tests`, `tests/Themis.Integration.Tests/Invariants` | A package reference of the two test projects only; no production project references it. |
| Property fixture (template database and warehouse `PROP-W2`) | The template every property sequence is cloned from: a database bootstrapped, migrated and seeded with the milestone 1 fixture by `Themis.Migrator` exactly as the fixture's own, plus a second warehouse of SE01, so that sequences move stock between two warehouses (step 11 brief). Each sequence runs on a `CREATE DATABASE ... TEMPLATE` clone that is dropped afterwards. | `tests/Themis.Integration.Tests/Invariants/InvariantPropertyTests.cs` (the warehouse), `tests/Themis.Integration.Tests/PostgresFixture.cs` (`CreateSeededDatabaseAsync`, `CloneDatabaseAsync`) | Created and dropped by the test class on the test server; no seeder or migration knows the warehouse, and the production migrator never clones a database. |
| Relay options for tests | `Outbox:Relay:Enabled` false in the pipeline test host; `Outbox:Relay:*` overrides in the host smoke tests to prove that invalid options stop the host. | `tests/Themis.Integration.Tests/Pipeline/PipelineTestHost.cs`, `tests/Themis.Kernel.Tests/HostSmokeTests.cs` | Host configuration of the test hosts only; `appsettings.json` ships the production defaults. |
| Setting definition seam (`ISettingDefinitionSeam`, `NoSettingDefinitionSeam`) | Definitions beside the settings catalogue for tests (milestone 2 step 2): the integration tests register `test.all_levels`, writable at every level, and `test.history_bearing`, since no milestone 2 definition allows a site or warehouse value or carries valid_from; the tests also write them to `kernel.setting_definition` beside the real catalogue through the seeder. The coverage test looks at the catalogue alone. | `src/Kernel/Themis.Kernel.Settings/SettingDefinitionSeam.cs`; `tests/Themis.Integration.Tests/Settings/SettingTestData.cs`; the test implementation `TestSettingDefinitionSeam` in `tests/Themis.Integration.Tests/Pipeline/TestSeams.cs` | Production registers `NoSettingDefinitionSeam`, which adds nothing (`TryAddSingleton`); the test host registers its seam first. |
| Setting write seam (`ISettingWriteSeam`, `NoSettingWriteSeam`) | A pause point in SETTING.SET and SETTING.CLEAR between the slot's version check and the insert, for the test that a write losing the race on the slot's version gets the same 412 as a stale If-Match (R-API-02, RR-45). | `src/Kernel/Themis.Kernel.Settings/SettingWriteSeam.cs`; the test implementation `TestSettingWriteSeam` in `tests/Themis.Integration.Tests/Pipeline/TestSeams.cs` | Production registers `NoSettingWriteSeam`, which returns at once (`TryAddSingleton`); the test host registers its seam first. |
| Purge options for tests | `Idempotency:Purge:Enabled` false in the pipeline test host, so no test waits on the timer; `Idempotency:Purge:*` overrides in the host smoke tests to prove that invalid options stop the host. | `tests/Themis.Integration.Tests/Pipeline/PipelineTestHost.cs`, `tests/Themis.Kernel.Tests/HostSmokeTests.cs` | Host configuration only; the production defaults are in `appsettings.json` and documented in code. |
| Test-only role passwords (`PostgresFixture.TestRolePassword`) | Since milestone 2 step 2a `db/bootstrap/01-roles.sql` sets no password (RR-65); the integration tests run it through Npgsql and then set the placeholder `themis` with `ALTER ROLE` on the three LOGIN roles, so they connect as each role. The psql script `db/bootstrap/02-role-passwords.psql` that sets real values is proven by CI's compose job instead. | `tests/Themis.Integration.Tests/PostgresFixture.cs` | Test project only; a real installation supplies its passwords through the psql variables, outside the repository (Build Brief, Secrets). |
| Test cleanup seam (`PostgresFixture.CleanupAsync`) | Since milestone 2 step 2b the D-60 triggers refuse UPDATE, DELETE and TRUNCATE of journal_entry, journal_line, inventory_entry, audit_event and setting_value even to the table owner. The one cleanup helper runs the tests' cleanup statements as the test server's superuser, in an explicit transaction that first runs `SET LOCAL session_replication_role = replica`, so the guard triggers (and the foreign key triggers) do not fire there. `TruncateAsync` and the audit cleanup of `IdentityTestData` use it. | `tests/Themis.Integration.Tests/PostgresFixture.cs`, `tests/Themis.Integration.Tests/Identity/IdentityTestData.cs` | Test project only. No role but a superuser may set session_replication_role (`pg_parameter_acl`, `LedgerImmutabilityTests`), and an architecture test fails when any file under `src` names it (`SessionReplicationRoleTests`). |
| Role probes (`RoleProbe`, `ProbeRoleReset`, `FixtureRoleInterceptor`) | RR-62: a test-only command whose scope resolver and handler read `SELECT current_user` on the persistence-internal connection, proving the dispatcher hands module code the connection as themis_app; and a fixture command that takes its connection from `IUnitOfWork.ForRoleAsync`, calls the settings reader, then reads raw (refused with 42501) or through the fixture's Entity Framework context with its role interceptor (succeeds). | `tests/Themis.Integration.Tests/Pipeline/RoleProbeSeam.cs` (route `/v1/test/role-probe`, mapped by `PipelineTestHost`); `tests/Fixtures/Themis.FixtureModule/Application/ProbeRoleResetHandler.cs`, `Infrastructure/RoleProbeStore.cs`, `Infrastructure/FixtureRoleInterceptor.cs` (route `/v1/fixture/counters/{id}/probe-role`) | Test project and fixture module only; `Themis.Host` maps neither route. Both run under the test-only `FIXTURE.TOUCH`. |
| Write-attempting query (`WriteAttemptQuery`) | RR-81: a test-only query under the test-only `FIXTURE.READ` whose handler tries to update the fixture table; the query dispatcher's transaction is read only, so PostgreSQL refuses it with 25006 and the query answers 500. | `tests/Themis.Integration.Tests/Pipeline/WriteAttemptQuerySeam.cs`, route `/v1/test/write-attempt` mapped by `PipelineTestHost` | Test project only; `Themis.Host` never maps it, and `FIXTURE.READ` is seeded by the integration tests alone. |
| Migrator environment for in-process runs (`PostgresFixture.MigratorEnvironment`) | RR-70: `Themis.Migrator` loads a fixture only in Development, Test or Testing. The tests call `Program.RunAsync(args, "Testing")` instead of changing the process environment. | `tests/Themis.Integration.Tests/PostgresFixture.cs` and every in-process caller of the migrator in the integration tests | Test project only; the production entry point `Program.Main` reads `DOTNET_ENVIRONMENT`, and unset means Production, where a fixture is refused with exit code 9. |
